# Runtime Prototype Specification

## 1. Objective

Build a small browser-based prototype to evaluate **PixiJS** and **Phaser 4** as the underlying runtime for an AI-learning platform.

The prototype is **not** intended to implement the final DSL, editor, learning system, or game framework.

Its purpose is to determine which runtime is the better foundation for a single long-lived 2D runtime.

### Primary question

> Can the runtime comfortably support animated, interactive, technical/mathematical 2D visualizations while also providing enough foundation for future 2D educational games?

Two independent implementations must be created:

1. **PixiJS implementation**
2. **Phaser 4 implementation**

The two prototypes should implement the same visual experience and expose approximately the same internal abstraction.

---

# 2. Target Architecture

The eventual platform architecture is:

```text
AI / Learning
      │
      ▼
MDX-based content
      │
      ▼
React / MDX Component
      │
      ▼
DSL
      │
      ▼
Runtime
      │
      ▼
PixiJS or Phaser 4
      │
      ▼
Browser
```

The prototype only covers the bottom portion:

```text
React Component
      │
      ▼
Prototype Runtime API
      │
      ▼
PixiJS / Phaser 4
      │
      ▼
Canvas
```

The application is entirely **TypeScript + React**.

MDX and the AI/Learning layers are out of scope for the prototype.

---

# 3. Frameworks

## Candidate A — PixiJS

[PixiJS](https://pixijs.com/?utm_source=chatgpt.com)

Use the current stable PixiJS release appropriate for the prototype.

Evaluate PixiJS as a **2D rendering and interactive scene runtime**, not merely as a canvas renderer.

Relevant capabilities to evaluate:

* scene graph
* containers/groups
* graphics primitives
* text
* sprites/images
* transforms
* events
* animation/ticker
* asset loading
* rendering performance
* camera implementation
* integration with React
* TypeScript ergonomics

PixiJS is the more minimal/focused candidate.

---

## Candidate B — Phaser 4

[Phaser](https://phaser.io/?utm_source=chatgpt.com)

Use the current stable Phaser 4 release appropriate for the prototype.

Evaluate Phaser as a **2D application/runtime**, not specifically as a game engine.

Relevant capabilities to evaluate:

* Game Objects
* Graphics
* Geometry
* Groups
* Text
* Sprites/images
* Tweens
* Time
* Input
* Cameras
* Scenes
* Audio
* asset loading
* physics integrations
* rendering performance
* React integration
* TypeScript ergonomics

Phaser's additional game-oriented functionality should not be treated as inherently negative; determine whether it provides useful infrastructure or unnecessary complexity.

---

# 4. Prototype Application

Create a single technical visualization demonstrating a **distributed-consensus algorithm**, using a simplified Raft election as the subject.

The algorithm itself does not need to be complete or formally accurate.

The purpose is to exercise the runtime's visual capabilities.

The visualization should contain approximately:

```text
             ┌───────────┐
             │  Node A   │
             │           │
             └───────────┘
                ↙     ↘
               /       \
              /         \
     ┌───────────┐   ┌───────────┐
     │  Node B   │   │  Node C   │
     │           │   │           │
     └───────────┘   └───────────┘
```

The exact visual design is intentionally left open.

The important requirement is that the scene be **visually composed from 2D primitives**, rather than generated by a graph-layout library.

---

# 5. Required Visual Capabilities

The prototype must demonstrate:

### Shapes

At minimum:

* circles or rounded rectangles
* rectangles
* lines
* arrows
* arbitrary paths or equivalent

### Text

Display:

* node labels
* state labels
* current term/step
* event descriptions

Text must be dynamically updateable.

### Composition

Objects must be grouped/composed so that a logical visual object can contain multiple primitives.

For example:

```text
node
 ├── body
 ├── label
 └── state indicator
```

The implementation should not require React components for every visual primitive.

---

# 6. Animation

The prototype must demonstrate several forms of animation.

### Object movement

A message/packet should travel from one node to another.

```text
A ───────────────► B
        ●
```

The moving object should follow a path rather than simply teleport.

### Property animation

Demonstrate changes such as:

* position
* scale
* opacity
* rotation
* size
* visual state

### Sequencing

Demonstrate:

```text
1. Node A changes state
2. RequestVote message moves to B
3. B responds
4. RequestVote message moves to C
5. C responds
6. A becomes leader
```

Some animations should execute sequentially and some in parallel.

### Easing

At least two animation/easing behaviors should be tested.

---

# 7. Controlled Simulation Time

This is a particularly important requirement.

The visualization must support:

```text
Play
Pause
Step
Reset
Speed
```

The user must be able to advance the visualization one logical step at a time.

The implementation should distinguish between:

```text
simulation state
```

and:

```text
rendering/animation state
```

The prototype should investigate how naturally each runtime supports this distinction.

---

# 8. Interaction

Demonstrate:

* click/tap on an object
* hover
* highlighting
* selecting an object
* keyboard interaction
* drag/pan if appropriate

At minimum:

```text
Click Node
    ↓
Node becomes selected
    ↓
Visual highlight
    ↓
Information displayed in React UI
```

Interaction between the React UI and the canvas runtime should be demonstrated.

---

# 9. Camera / Viewport

The prototype must support:

* zoom in
* zoom out
* pan
* reset view
* focus on an object

The visualization should remain usable when the scene becomes larger than the viewport.

---

# 10. Simple Physics / Simulation

Implement a small independent experiment in the same prototype.

For example:

```text
●
│
│ gravity
▼
──────────── ground
```

The object should demonstrate:

* position
* velocity
* acceleration
* gravity
* simple collision with a ground plane

This does **not** need a sophisticated physics engine.

The objective is to determine how naturally the runtime can support simple simulations and whether an external physics library would be necessary later.

---

# 11. Performance Experiment

Create a separate test scene containing approximately:

* 100 objects
* 500 objects
* 1,000 objects

Objects should include a mixture of:

* geometric shapes
* text
* lines
* animated objects

Measure qualitatively and, where practical, quantitatively:

* initialization time
* rendering smoothness
* animation performance
* interaction performance
* memory behavior

The goal is not to benchmark maximum theoretical performance.

The goal is to determine whether either runtime creates obvious problems for AI-generated technical visualizations.

---

# 12. React Integration

The runtime must live inside a normal React component.

Conceptually:

```text
React Application
       │
       ├── Controls
       ├── Information Panel
       └── Visualization
                │
                └── Runtime
                     │
                     └── Canvas
```

React should remain responsible for:

* UI controls
* surrounding application UI
* selected-object information
* runtime lifecycle

The runtime should remain responsible for:

* canvas rendering
* visual objects
* animation
* simulation
* canvas interaction

Avoid implementing the visual scene as a large React component tree.

---

# 13. TypeScript Requirements

Both implementations must be:

* TypeScript-first
* strict TypeScript where practical
* minimal dependencies
* no unnecessary framework abstractions
* no generated code
* no framework-specific DSL

The prototype should expose a **small internal runtime abstraction** so that the two implementations can be compared.

The abstraction does not need to become the final runtime API.

Its purpose is simply to prevent the prototype from becoming a direct collection of PixiJS/Phaser calls.

---

# 14. Out of Scope

Do **not** implement:

* the final DSL
* a DSL parser
* an editor
* MDX integration
* AI integration
* learning/content models
* authentication
* persistence
* backend services
* multiplayer
* production asset pipeline
* sophisticated physics
* 3D
* WebAssembly
* complex game mechanics

The prototype should remain focused on runtime evaluation.

---

# 15. Evaluation Criteria

After implementing both versions, evaluate each runtime on:

### Technical visualization

* How easy is it to create precise 2D scenes?
* How good are the geometry primitives?
* How easy is dynamic geometry?
* How easy is text and labeling?
* How easy is object composition?

### Animation

* How easy is arbitrary property animation?
* How easy is sequencing?
* How easy is synchronization?
* How easy is pause/step/reset?
* How easy is deterministic simulation?

### Interaction

* How easy is object-level interaction?
* How easy is hit testing?
* How easy is selection/highlighting?
* How easy is keyboard/touch input?

### Simulation

* How easy is a custom simulation loop?
* Can simulation time be controlled independently from rendering?
* How easy is simple physics?

### React

* How clean is the React integration?
* Are lifecycle issues easy to manage?
* Can the runtime remain isolated from React?

### Agent/LLM development

This is a major criterion.

Evaluate:

* quality of generated TypeScript
* ease with which a coding agent understands the API
* quality of documentation/examples available to agents
* frequency of incorrect API assumptions
* ease of debugging generated code
* API consistency
* source-code readability
* amount of boilerplate required
* ability of an agent to extend the runtime without introducing architectural problems

### Future games

Determine whether the runtime can reasonably support:

* sprites
* animation
* audio
* cameras
* collisions
* simple physics
* game input
* game state
* particles
* larger interactive scenes

without requiring a second runtime.

---

# 16. Licensing Requirements

The selected runtime must satisfy all of the following:

* open source
* permissive license
* commercial use permitted
* closed-source applications permitted
* no requirement to publish customer/application source
* no runtime royalties
* no per-user fees
* no per-game fees
* no one-time runtime licensing fee
* no mandatory subscription to distribute applications

Optional commercial editors or development tools are irrelevant because the project will use its **own editor/tooling**.

The evaluation concerns the **runtime/library itself and its mandatory runtime dependencies**.

---

# 17. Final Decision

The prototype should produce a short comparison covering:

```text
PixiJS
   vs
Phaser 4
```

with particular emphasis on:

1. Technical/mathematical 2D visualization
2. Animation
3. Interaction
4. Controlled simulation
5. React/TypeScript integration
6. Agent/LLM development experience
7. Future 2D educational games
8. Engineering effort required to build the runtime layer
9. Performance
10. Licensing

The goal is to select **one runtime**.

Maintaining separate PixiJS and Phaser implementations in the final product is explicitly out of scope.
